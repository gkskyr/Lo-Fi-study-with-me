BÖLÜM 1 — PROJE MİMARİSİ VE GENEL BAKIŞ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

koZan: Öğrencilere yönelik bir çalışma platformu. İki temel modu var:
  • Topluluk Odaları  → birden fazla kullanıcının sesli katıldığı ortak çalışma odaları
  • Kişisel Oda       → tekli, denetim destekli pomodoro/timer çalışma oturumları

Teknik yığın:
  Backend  → NestJS (Node.js), port 3001
  Frontend → Next.js 15 (App Router), port 3000
  Veritabanı → PostgreSQL + Prisma ORM
  Önbellek/Varlık → Redis (Socket.IO için gerekli)
  Gerçek zamanlı → Socket.IO (WebSocket gateway)
  Ses/Video → Agora RTC (topluluk odaları için)
  Auth → JWT (access + refresh token), e-posta doğrulama
  State → Zustand (frontend)
  Depolama (denetim) → IndexedDB (tarayıcıda, sunucuya gönderilmiyor)

BÖLÜM 4 — DENETİM SİSTEMİ (MEVCUT DURUM)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Denetim iki farklı yöntemle çalışır:

── KAMERA DENETİMİ (NOTEBOOK modu) ──────────────────────────────────────────

Kalibrasyon:
  Kullanıcı kamerayı açar. Ekranda yeşil bir bounding box gösterilir
  (top:25%, left:25%, width:50%, height:50%). Kullanıcı defterini/kitabını
  bu kutunun içine koyar ve "Kaydet" der. O anki görüntünün bu bölgesi
  32x32 piksel gri tonlama matrisine (thumbprint) indirgenerek IndexedDB'ye
  kaydedilir.

Check-in:
  Tur bittiğinde CheckInModal açılır. Kullanıcı "Hazırım" der, 3 saniyelik
  geri sayım başlar. Süre dolunca aynı yeşil kutu bölgesinin anlık görüntüsü
  alınır, yeni thumbprint hesaplanır, referansla MAD (Mean Absolute Difference)
  karşılaştırması yapılır. Benzerlik > 0.65 → geçti.

Algoritma: 32x32 MAD
  - Her piksel gri tona çevrilir (0.299*R + 0.587*G + 0.114*B)
  - İki 1024 elemanlı dizinin her elemanının mutlak farkı ortalaması
  - similarity = 1 - (ortalama_fark / 255)
  - Aynı obje aynı pozisyonda → ~0.85-0.95
  - Tamamen farklı sahne → ~0.40-0.60
  - Eşik: 0.65

── PC DENETİMİ (PC modu) ────────────────────────────────────────────────────

Kalibrasyon:
  Kullanıcı çalışma materyalinin görselini (PNG/JPG) dosya olarak yükler.
  Bu görsel dHash algoritmasıyla 256 bitlik boolean diziye dönüştürülür
  ve IndexedDB'ye kaydedilir.

Check-in:
  getDisplayMedia() ile ekran paylaşımı istenir. Kullanıcı ekranı seçer.
  400ms beklendikten sonra tam ekran görüntüsü alınır, dHash hesaplanır,
  referans dHash ile karşılaştırılır. Benzerlik > 0.72 → geçti.

Algoritma: 256-bit dHash (gradient hash)
  - Görsel 17x16 piksel boyutuna küçültülür
  - Her satırda soldan sağa komşu piksel parlaklıkları karşılaştırılır
    (sol < sağ ise true, değilse false)
  - 16 satır × 16 karşılaştırma = 256 bit
  - Tamamen farklı iki görsel → ~%50 benzerlik (rastgele coin flip gibi)
  - Aynı içerik → >%85 benzerlik
  - Eşik: 0.72

IndexedDB yapısı:
  Veritabanı adı: "kozan-monitoring"
  Object store: "calibration"
  Anahtar: "mon-{userId}" (userId = accessToken'ın son 16 karakteri)
  Değer: { cam?: number[], pc?: boolean[] }

BÖLÜM 5 — BACKEND API REFERANSI
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Auth:
  POST /auth/register        { email, username, name, password }
  POST /auth/verify-email    { email, code }
  POST /auth/login           { email, password }
  POST /auth/refresh         { refresh_token }

Odalar:
  GET  /rooms                → Room[]
  GET  /rooms/:id            → Room
  GET  /rooms/:id/agora-token (JWT gerekli) → { token, uid, channelName }

Sorular:
  GET  /rooms/:roomId/questions → Question[]
  POST /questions              (multipart/form-data: roomId, content, files[])
  POST /questions/:id/vote
  GET  /questions/:id/answers
  POST /questions/:id/answers  (multipart/form-data: content, files[])

Çalışma Oturumları (JWT zorunlu):
  POST   /study-sessions           → StudySession oluştur
  PATCH  /study-sessions/:id/round → completedRounds++ yap
  POST   /study-sessions/:id/checkin → { round, passed, monitoringType }
  PATCH  /study-sessions/:id/end   → XP hesapla, oturumu kapat
  GET    /study-sessions/me        → Kullanıcının son 20 oturumu

XP/Rol sistemi:
  BEGINNER    → 0-499 XP
  EXPERIENCED → 500-1999 XP
  INSTRUCTOR  → 2000+ XP
  Oturum XP formülü: (completedRounds * 10) + monitoringBonus
  monitoringBonus = round((passedCheckIns / totalCheckIns) * completedRounds * 5)

Teachable Machine modeli o objeyi tanımayı öğrenir, sonra check-in'de
kameraya bakarak "bu obje var mı?" sorusunu cevaplar.

Bu yaklaşımda üç katmanlı hata yaptım:

1. MİMARİ HATA: Model eğitimi OTURUM SIRASIN'DA çalışıyordu. Kullanıcı
   ilk check-in'e geldiğinde model eğitilecekti. Bu çok geç. Kullanıcı
   bana "oturuma başlamadan önce modeli tanıtmam lazım" dedi. Haklıydı.
   Kalibrasyon oturum öncesinde olmalı. Bunu anlamamam başlı başına bir
   tasarım hatasıydı.

2. TEKNİK HATA: TensorFlow.js tarayıcıda çalışmadı. Hata mesajı:
   "No backend found in registry — initializeBackendsAndReturnBest"
   Bu hata TF.js'in WebGL veya CPU backend'ini kaydedemediği anlamına
   geliyordu. @tensorflow/tfjs paketi yüklüydü ama Next.js'in SSR/RSC
   ortamıyla çakışıyordu. Dynamic import denedim, farklı import sıraları
   denedim, olmadı. TF.js tarayıcı ortamına özgü global state bekliyor,
   Next.js App Router bunu kırıyor.

3. FAZLA KARMAŞIK: MobileNet + transfer learning, kullanıcı obje sınıflandırması
   için bu projeye overkill. Kullanıcının ihtiyacı "aynı obje orada mı?"
   sorusunu cevaplamak — bu bir sınıflandırma problemi değil, bir benzerlik
   problemi.

─── İKİNCİ YAKLAŞIM: Canvas tabanlı karşılaştırma ──────────────────────────

TF.js'i tamamen çıkardım. Saf HTML Canvas API ile şunları yaptım:

Kamera için:
  32x32 grayscale thumbprint + MAD (Mean Absolute Difference)
  Mantık: "referans karedeki piksel dağılımı şimdiki karedekiyle ne kadar benzer?"

PC için:
  256-bit dHash (difference hash / gradient hash)
  Mantık: "görüntünün soldan-sağa parlaklık değişim yönleri ne kadar benzer?"

Kamera algoritması (32x32 MAD) kamera denetimi için makul görünüyor ama
henüz canlı test yapılmadı. Asıl sorun PC denetiminde yaşandı:

ASIL SORUN — 32x32 MAD, PC için çok zayıf:
  Kullanıcı bana dedi ki: "İnek fotoğrafını referans olarak yükledim,
  ekranım YouTube'daydı, %76 doğrulukla geçti."

  Neden böyle oldu? 32x32 MAD, piksellerin ORTALAMA PARLAKLIĞINI karşılaştırır.
  Bir inek fotoğrafının (çimenlik, açık renkli) ile YouTube'un koyu arayüzünün
  ortalama parlaklıkları tesadüfen benzer çıktı. Algoritma içeriği görmüyordu,
  sadece genel tona bakıyordu.

  Düzeltme olarak dHash'e geçtim. dHash MUTLAK parlaklığa bakmıyor, yerine
  "sol piksel sağdan daha karanlık mı?" gibi yön bilgilerine bakıyor. Bu sayede
  bir ineğin gradiyan yön deseni bir YouTube sayfasından çok farklı çıkıyor.
  İki tamamen farklı görüntü dHash ile ~%50 benzerlik gösteriyor (teorik olarak
  coin flip'e eşdeğer), eşik 0.72'ye ayarlandı.

Ancak bu düzeltme de canlı test edilmedi. Yani gerçekte ne kadar iyi çalıştığını
bilmiyorum. Eşikler (kamera 0.65, PC 0.72) teoriye dayanıyor, ampirik değil.

─── KAMERA AÇILMAMA SORUNU ───────────────────────────────────────────────────

Bir de kameranın açılmaması sorunu vardı. Kullanıcı denetim test sayfasında
kamerayı açmaya çalıştığında video elementi siyah kaldı.

Root cause: React'ın koşullu render mekanizması.
  Video elementi sadece "ready" adımında render ediliyordu.
  getUserMedia().then() callback'i içinde hem stream alıp hem
  videoRef.current.srcObject = stream demeye çalışıyordum.
  Ama o an video elementi DOM'da yoktu — state henüz güncellenmemişti.

Düzeltme:
  1. .then() içinde: streamRef.current = stream; setState("ready"); // sadece bu
  2. useEffect([step]) içinde: video DOM'a geldikten sonra srcObject ata

Bu düzeltme CalibrationView.tsx ve /denetim/page.tsx'e uygulandı.
CheckInModal.tsx'te kamera farklı şekilde açılıyor (video elementi her zaman DOM'da),
orada bu sorun teorik olarak yok ama yine test edilmedi.
