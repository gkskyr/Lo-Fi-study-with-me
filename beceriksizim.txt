BU BELGE NE:
  Öğrenci çalışma oturumu sırasında PC ekranının denetlenmesi için yazılan
  monitoring modülünün başından sonuna tüm teknik tarihi. Denenen her yöntem,
  neden çalışmadığı, mevcut mimari durum ve gerçek çözüm yolu burada.

--------------------------------------------------------------------------------
PROBLEM TANIMI
--------------------------------------------------------------------------------

Kullanıcı (öğrenci) kalibrasyon aşamasında bir "referans materyal" görseli
sisteme tanıtıyor. Bu materyal bir ders kitabı, defter, tablet ekranı veya
herhangi bir fiziksel nesne olabilir. Çalışma oturumu boyunca periyodik olarak
öğrencinin PC ekran görüntüsü alınıyor ve bu ekranda referans materyalin
görünüp görünmediği doğrulanıyor.

GİRDİLER:
  - Referans görsel: kamerayla veya dosya yüklemeyle alınmış, referans nesnenin
    close-up fotoğrafı. Perspektif bükülmesi, kötü ışık, gürültü olabilir.
  - Ekran görüntüsü: dijital, temiz, tam ekran ya da tarayıcı sekmesi.
    Referans nesne ekranın küçük bir köşesinde, belki 80x60 piksel alanda.

TEMEL ZORLUK: "Cluttered Scene Sub-image Localization"
  Bu problem bilgisayarlı görü literatüründe en zor problemlerden biridir.
  Bir görüntüdeki küçük bir nesneyi başka bir karmaşık sahnede bulmak,
  global feature matching ile pratikte çözülemiyor. Bunu baştan bilseydik
  belki 3 hafta kurtarırdık.

YÖNTEM 1: dHash (Difference Hash)
--------------------------------------------------------------------------------

NE YAPTI:
  Görsel 8x8'e küçültülür, her piksel komşusundan büyük mü küçük mü diye
  bakılır, 64-bit binary hash üretilir. İki hash arasındaki Hamming mesafesi
  benzerlik skoru olarak kullanılır.

NEDEN ÇALIŞMADI:
  dHash global bir imzadır. Ekran görüntüsünün tamamına bakıyor,
  referans nesnenin ekranın bir köşesinde olup olmadığını anlayamıyor.
  Kullanıcı ekranı değiştirdiğinde hash tamamen değişiyor.

DOSYA DURUMU: frontend/src/lib/monitoring.ts içindeki diffHash, hashSimilarity,
  fileToDiffHash fonksiyonları SİLİNDİ.

YÖNTEM 3: NCC (Normalized Cross-Correlation) — Template Matching
--------------------------------------------------------------------------------

NE YAPTI:
  Referans görseli farklı ölçeklerde (200px, 120px, 80px, 50px genişlikte)
  ekran görüntüsü üzerinde piksel piksel kaydırarak arar. Her konumda
  ortalama çıkarılmış normalize çarpım toplamı hesaplanır. En yüksek NCC
  skoru similarity olarak döner.

KOD YERI: frontend/src/lib/templateMatch.ts (silindi)

NEDEN ÇALIŞMADI:
  1. Ölçek duyarlılığı: Referans 80px'e scale edilmişken ekranda 60px'lik
     nesne varsa eşleşme yok.
  2. Rotasyon duyarlılığı: 5 derecelik eğim NCC'yi mahveder.
  3. False positive problemi: 32-50px ölçekte NCC yeterince discriminative
     değil. Rastgele yamalar "eşleşiyor". Test: inek fotoğrafı referans,
     YouTube sayfası → %58 ile GEÇER. Hiçbir anlam ifade etmiyor.
  4. Perspektif farkı: Referans kamerayla çekilmiş (bükülmüş, ışıklı),
     ekran görüntüsü dijital ve temiz. NCC bu farkı kaldıramıyor.

DOSYA DURUMU: frontend/src/lib/templateMatch.ts SİLİNDİ.

YÖNTEM 4: ORB (FAST-9 corners + BRIEF-256 descriptors) — Frontend
--------------------------------------------------------------------------------

NE YAPTI:
  Her iki görselde FAST-9 algoritmasıyla köşe noktaları (keypoint) bulur.
  Her köşe etrafındaki 31x31 piksellik bölgeye BRIEF-256 uygular:
  256 rastgele piksel çifti karşılaştırması → 256-bit binary descriptor
  (8 adet uint32 olarak saklanır). İki descriptor arasındaki benzerlik
  Hamming mesafesiyle ölçülür (XOR + popcount).

  Lowe's ratio test: best_dist < maxDist && best_dist < second_best * 0.75
  Bu test belirsiz eşleşmeleri eler.

  Multi-scale: Referans 4 farklı ölçekte işlenir [200, 120, 80, 50 px],
  en iyi ölçeğin skoru döner. Ekran görüntüsü 640px'e scale edilir.

KOD YERI: frontend/src/lib/orb.ts (silindi, backend'e taşındı)

NEDEN ÇALIŞMADI (FRONTEND):
  1. Güvenlik açığı: Frontend'deki her şey DevTools ile bypass edilir.
     Öğrenci JavaScript'i manipüle edebilir.
  2. False positive: Ratio test olmadan %58 false positive (inek/YouTube).
     Ratio test eklenince azaldı ama hala sorunlar vardı.
  3. Browser'da canvas API ile performans sorunları.

KARAR: Backend'e taşındı.

YÖNTEM 6: LightGlue (SuperPoint + LightGlue) — Python Mikroservis
--------------------------------------------------------------------------------

NE YAPTI:
  Python FastAPI servisi olarak eklendi (port 8001).
  SuperPoint: Öğrenilmiş keypoint detector (elle yazılmış FAST yerine
  neural network tabanlı). Işık, açı ve ölçek varyasyonlarına daha dayanıklı.
  LightGlue: Graph Neural Network tabanlı feature matcher. İki görüntü
  arasındaki keypoint çiftlerini öğrenilmiş confidence ile eşleştirir.
  RANSAC olmadan geometrik filtering yapıyor (öğrenilmiş).

  NestJS monitoring.service.ts artık Python servise HTTP POST yapıyor.
  Referans görseli ham byte olarak veritabanında (refImage: Bytes) saklanıyor.

KOD YERI: matcher/main.py (aktif), matcher/requirements.txt
BACKEND: backend/src/monitoring/monitoring.service.ts (fetch ile HTTP call)
KURULUM:
  pip install git+https://github.com/cvg/LightGlue.git
  pip install fastapi uvicorn pillow numpy python-multipart
  pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
  python -m uvicorn main:app --port 8001

MEVCUT DURUM (ÇALIŞMIYOR — AYNI TEMEL SORUN):
  Test: Referans görsel ekranda küçük göründüğünde → %0 benzerlik.
  Test: Farklı sayfa → %8.4 benzerlik → false positive (threshold=0.08).

  NEDEN ÇALIŞMIYOR:
  LightGlue da global matching yapıyor. Her iki görsel 640x480'e resize
  ediliyor. Referans nesne ekranda 80x50 piksel alanda görünüyorsa:
    - Referans görsel: nesne 640x480 piksele yayılmış = büyük, detaylı
    - Ekran görüntüsü: nesne 80x50 piksel = küçük, detaysız
  Ölçek farkı ~8x. SuperPoint her ikisinde keypoint buluyor ama farklı
  ölçekte oldukları için LightGlue bunları eşleştiremiyor.

  Bu ORB'un RANSAC eksikliğinden farklı bir problem. RANSAC eklesen de
  çözemezsin — keypoint'ler zaten eşleşmiyor, spatial verification yapmak
  için önce eşleşme gerekiyor.

THRESHOLD SORUNU:
  matcher/main.py içinde THRESHOLD = 0.08 (8%)
  Bu çok düşük. Herhangi bir sayfa 5-10% false positive verebiliyor.
  Ama threshold'u yükseltirsen (örn. 0.20) gerçek pozitifler de
  eşik altında kalıyor çünkü küçük nesnede zaten az eşleşme var.

GERÇEKÇİ ÇÖZÜM YOLLARI (SIRASIZ)
--------------------------------------------------------------------------------

YÖNTEM A: Multi-scale Sliding Window + LightGlue (DOĞRU AMA YAVAŞ)
  Ekran görüntüsünü farklı pencere boyutlarında (128x128, 256x256, 384x384)
  kaydırarak her pencere için LightGlue çalıştır. En yüksek skor alınan
  pencere = nesnenin yeri.
  DEZAVANTAJ: Bir ekran görüntüsü için ~50-200 forward pass = 10-30 saniye.
  CPU'da pratik değil. GPU ile 2-3 saniyeye düşebilir.

YÖNTEM B: YOLO Custom Object Detection (UZUN VADELİ EN DOĞRU)
  Veri: Her kullanıcının referans görseli + ekran görüntüsü çifti.
  Ultralytics YOLOv11 ile few-shot object detection.
  DEZAVANTAJ: Her kullanıcı için ayrı model eğitmek pratik değil.
  Genel bir model için binlerce etiketli veri lazım.

YÖNTEM C: SORUYU DEĞİŞTİR — CLIP Doğru Sorulunca Çalışır
  "Referans nesne ekranda küçük görünüyor mu?" sorusu yerine
  "Öğrenci referans materiyal ile ilgili içerik görüyor mu?" sor.

  Örnek: Referans = matematik ders kitabı kapağı.
  Soru: "Ekranda matematik ile ilgili bir şey var mı?"

  Bu soru için CLIP mükemmel çalışır. Ekranın tamamı "matematik içeriği"
  mi yoksa "YouTube/oyun/sosyal medya" mı diye ayrıştırabilir.

  PROBLEM: "Öğrenci ekranında referans materyalin kendisini görmeli"
  kısıtı varsa bu yaklaşım işe yaramaz. Referans kitabı kapatıp PDF
  okursa geçer. Use case'e bağlı.

YÖNTEM D: LoFTR (Detector-Free Feature Matching)
  github: kornia/kornia (zaten kurulu — LightGlue bağımlılığı olarak geldi)
  LoFTR dense matching yapıyor: keypoint detect etmeden transformer ile
  her piksel için matching yapıyor. Büyük ölçek farklarını daha iyi kaldırır.

  Kullanım:
    from kornia.feature import LoFTR
    matcher = LoFTR(pretrained="outdoor")  # veya "indoor"

  AVANTAJ: Küçük nesnelerde ORB/LightGlue'dan çok daha iyi.
  Kornia zaten kurulu (pip install git+... ile LightGlue ile birlikte geldi).
  DEZAVANTAJ: CPU'da LightGlue'dan ~2x yavaş.

YÖNTEM E: Vision LLM (Gemini/GPT-4o) — Gizlilik Sorunu
  Gemini 2.5 Flash API veya GPT-4o-mini: İki görseli modele gönder,
  "referans nesne ekranda görünüyor mu?" diye sor.
  AVANTAJ: Kesinlikle çalışır. Ölçek, açı, perspektif hiç sorun değil.
  DEZAVANTAJ: Ekran görüntülerini Google/OpenAI'a gönderiyorsun.
  Öğrencilerin ekran içerikleri 3. şahıs sunucularına gidiyor.
  Bu proje için kabul edilemez bulundu.

--------------------------------------------------------------------------------
ÖNERİ: LoFTR ile Dene (Mevcut Kurulumda Var)
--------------------------------------------------------------------------------

Kornia zaten kurulu. matcher/main.py'yi LoFTR kullanacak şekilde değiştir:

  from kornia.feature import LoFTR
  import kornia

  matcher = LoFTR(pretrained="outdoor").eval()

  def match_loftr(ref_bytes, screen_bytes):
      img0 = load_as_gray_tensor(ref_bytes)    # [1,1,H,W] float32
      img1 = load_as_gray_tensor(screen_bytes)

      input_dict = {"image0": img0, "image1": img1}
      with torch.inference_mode():
          correspondences = matcher(input_dict)

      conf = correspondences["confidence"]
      num_good = (conf > 0.9).sum().item()
      score = num_good / max(img0.shape[-1] * img0.shape[-2] / 1000, 1)
      return score

  LoFTR "outdoor" weights ~100MB, ilk çalıştırmada otomatik indirir.

Eğer LoFTR da çözemezse multi-scale sliding window + LoFTR kombinasyonu
dene: 3-4 farklı crop bölgesi için çalıştır, max skoru al.
